# ADR-0007：音箱持有播放队列，服务端跟随

- **状态**：Proposed（方向已于 2026-11-22 认可；按“实施步骤”分步落地，每步测试服实机验收，全部完成后改为 Accepted）
- **日期**：2026-11-22
- **关联**：ADR-0003（Source 抽象）、ADR-0004（状态权威）

## 上下文

### 现状：服务端逐首指挥

服务端每次只向音箱下发**一首**（`play_by_music_url`，一个 audio item），靠“时长 + `delay_sec`”的计时器推测歌曲结束，再下发下一首。音箱自带列表循环（`loop_type: 1`），只有一首的列表会在结尾**从头重放**。

在测试服（OH2P）上实测得到以下问题：

| 问题 | 实测 |
|---|---|
| 切歌晚到，用户听到“当前歌曲从头播几秒再切” | 计时器到点后，服务端切歌需要 3.4–6.4 s，但只提前了 2 s |
| 小米云间歇卡顿 | `player_stop` 和 `play_by_music_url` 都会遇到约 31 s 的送达延迟，1 小时内 3 次 |
| 服务端一旦停住，音箱就“单曲循环” | 已修复两处诱因（切歌前停止超时、顺序播放结束），但逐首模型下这类问题会反复出现 |
| 拿不到播放进度 | `player_get_play_status` 只返回 `status/volume/loop_type`；Jellyfin 不为音箱建立会话；MIoT 规格没有进度 |

2026-11-22 已经去掉计时器到点后的状态查询，自动切歌也不再先停止（`auto_next_preplay_stop=false`），正常时切换时间降到 1–2 s。剩下的延迟在下发命令本身（0.4–7 s，偶发 31 s），只要逐首经过小米云就消除不了。

### 实验结论（测试服 OH2P，2026-11-22）

| 问题 | 结论 |
|---|---|
| 一个 `player_play_music` 带多个 audio item | ✅ 音箱放完一首后**在本地**接着放下一首，不经过云端 |
| `startaudioid` 指定起始项 | ✅ 有效 |
| `player_play_operation` 的 next/prev/play | ❌ 对我们下发的列表无效 |
| 暂停 / 恢复 / 跳转 | `pause`（media=app_ios）能暂停；暂停期间 `status` 仍为 1。恢复：`play`（app_ios / common / 不带 media）、再次 `pause`、`resume`、`continue` 都**不能恢复**（`toggle` 遇云端卡顿未得出结论）。`pause`（media=common）不会暂停。跳转：`player_set_positon` 返回成功但不生效，`player_set_position` 返回 500。**结论：无法原地恢复，也无法跳转** |
| 列表长度 | 181 项（40 KB）可以接受 |
| `play_behavior` | `ENQUEUE` / `REPLACE_ENQUEUED` / `APPEND` 都按替换处理：立即打断当前曲并改播新列表。**不支持追加** |
| 静音哨兵续接 | 窗口 [20 s 曲, 60 s 静音]：音箱放完曲目后拉静音，服务端 0.02–0.05 s 内发现并下发新窗口；新窗口只替换静音，未打断任何曲目；曲间多出的静音 = 下发耗时（3 轮：1.4 / 1.7 / 4.0 s） |
| `player_set_loop` | 0 = 单曲循环；1 = 列表循环；2 = 顺序播完后停止（`status` 变 0）；3 = 放完继续（随机，待用更多曲目确认） |
| 音箱什么时候拉流 | **在切到该曲时才请求**，误差约 0.4 s；不会提前缓冲下一首。本地文件、Jellyfin（直连/代理）、支持或不支持 Range 的直链、无长度分块、按实时码率推流、YouTube 中转都成立 |
| 请求形态 | 有 Content-Length 时同一首会在 0.1 s 内连发 3–4 个请求（读开头后中断、读末尾 128 B 的 ID3 标签、完整下载）；无长度分块只发 1 个 |
| 实时推流 | 音箱先缓冲约 4 s 再出声，下一首的请求相应晚约 4 s |
| 长暂停 | 暂停 6 分钟后没有重新请求（整首已缓冲） |
| 格式 | mp3 / flac / m4a / wav 均可 |
| 现有代理令牌 | `/proxy/music?urlb64=t.…` 只存在内存里，**服务重启后全部失效** |

## 决策

**把歌曲之间的切换交给音箱：服务端一次下发一串曲目，音箱在本地顺序/循环播放；服务端根据音箱的拉流请求跟随当前曲目。只有用户操作才经过小米云。**

### 组件

```
SourceResolver（现有 Source 插件，ADR-0003）
    只负责：给出一首歌“此刻可用”的真实音频（URL + headers），或说明需要实时转码
        │
StreamGateway（新增，xiaomusic 内的 HTTP 端点）
    - 每首歌一个稳定地址：/stream/v1/<did>/<queue>/<index>/<source>/<item>?sig=…
    - 音箱请求时才调用 SourceResolver；按来源转发、代理或实时转码
    - 把同一首歌的一串请求合并成一个 TrackFetched 事件
        │
SpeakerQueue（新增，每设备一个）
    - 按歌单、播放模式生成要下发的“窗口”（一段曲目）、起始项和 loop_type
    - 随机模式由服务端打乱后下发；会话内顺序稳定（沿用 ADR-0004 补充决策）
        │
PlaybackFollower（新增，每设备一个）
    - 消费 TrackFetched，更新当前曲目、开始时间与状态
    - 计时器只做兜底
        │
SpeakerClient（新增，唯一调用小米云的地方）
    - play_queue / stop / set_loop / set_volume / tts / status
```

`DevicePlayer`（由 `device_player.py` 拆出）只负责编排：接收命令 → 让 SpeakerQueue 生成列表 → SpeakerClient 下发 → PlaybackFollower 跟随。

### 操作行为

| 操作 | 行为 | 是否经过云端 |
|---|---|---|
| 自动切歌 | 音箱本地完成；StreamGateway 收到请求 → TrackFetched → Follower 更新 | 否 |
| 点播一首 / 换歌单 | 生成新列表，从目标曲开始下发（`startaudioid`） | 1 次 |
| 手动下一首 / 上一首 / 跳到某首 | 重发当前列表，`startaudioid` 指向目标曲 | 1 次 |
| 停止 | `player_stop` | 1 次 |
| 改播放模式 | 不打断当前曲：只改 `loop_type`（一次云端调用）；需要重新排序时（切换随机），在下一次 TrackFetched 时以当前曲为起点重发 | 1–2 次 |
| 歌单内容同步更新 | 标记队列过期，在下一次续接窗口或用户操作时生效 | 0–1 次 |
| 窗口放完 | 音箱切到窗口末尾的静音哨兵 → 服务端下发下一个窗口（见“窗口与续接”） | 1 次（每个窗口一次） |

### 播放模式映射

| 播放模式 | 下发窗口 | `loop_type` |
|---|---|---|
| 单曲循环 | 仅当前曲 | 0 |
| 列表循环 | 从当前曲起按会话顺序取 N 首（到末尾后接回开头），末尾加静音哨兵 | 1 |
| 顺序播放 | 从当前曲起取 N 首，末尾加静音哨兵；最后一个窗口到歌单末尾为止、不加哨兵 | 2（播完停止） |
| 单曲播放 | 仅当前曲 | 2 |
| 随机播放 | 服务端打乱后的会话顺序，同列表循环 | 1（不使用 3，以保持服务端知道顺序） |

不随机时，列表使用**歌单原本的顺序**（Jellyfin 歌单的编排顺序、本地目录的库顺序），不再按歌名排序。两条播放入口按同一规则生成列表。

### 窗口与续接

每次只下发一个窗口（默认 N=20 首，可配置），不下发整个歌单。音箱不支持追加（`play_behavior` 都按替换处理），任何续接都会替换当前队列，因此续接必须发生在**不在放歌**的时刻：

1. 需要续接的窗口末尾放一个**静音哨兵**（StreamGateway 提供的固定地址，内容为足够长的静音，例如 60 s）。
2. 音箱放完窗口最后一首后，会在本地切到哨兵并拉取它；StreamGateway 产生 `WindowExhausted` 事件。
3. 服务端立即以下一首为起点下发新窗口。新窗口替换的只是正在播放的静音，不打断任何一首歌。
4. 歌曲之间多出的静音等于这一次下发的耗时（平时 0.5–1 s，每 N 首一次）。即使小米云卡顿约 31 s，听到的也只是静音；哨兵长度要大于这类卡顿，避免循环回窗口开头。
5. 若哨兵放完仍未收到新窗口（下发失败），音箱会按 `loop_type` 回到窗口开头；Follower 会把这次 TrackFetched 识别为“过期窗口”，并重新下发。

手动操作（点播、切歌、跳歌）总是以目标曲为起点下发一个新窗口；上一首会生成包含前一首的窗口。

### StreamGateway 规则

1. **地址稳定、重启后仍有效**：地址本身携带 `did`、队列号、序号、来源和曲目 ID，并用持久化在 `conf/` 的密钥做 HMAC 签名。服务端重启后，旧队列地址仍能按来源和曲目 ID 解析，不依赖内存里的令牌。
2. **不能变成开放代理**：只接受签名有效的地址，签名覆盖路径里的全部字段；不接受任意 URL。地址允许音箱匿名访问（音箱无法携带凭据），与现有媒体数据面一致。
3. **请求合并**：同一 `(did, queue, index)` 在 3 s 内的请求视为一次拉流。只请求文件末尾的 Range（读取 ID3/索引的探测）不单独算一次切换。`Range` 起点在文件中段的请求视为续传，不产生 TrackFetched。
4. **按来源处理**：
   - 本地文件：直接提供文件（支持 Range）。
   - 直链：反向代理并透传 Range。
   - Jellyfin：服务端带登录令牌请求，令牌不出现在给音箱的地址里。
   - 网站来源（YouTube 等）：拉流时才解析、启动实时转码（取代 `site_media` 在 Source 层调用 `RelayRuntime.prepare_link`，落实 ADR-0003）。
   - 在线插件：拉流时才调用插件取地址。
5. **过期队列**：请求的 `queue` 不是当前队列时，仍然提供音频（音箱可能还在播旧列表的缓冲），同时把事件交给 Follower 判断是否需要重新同步。

### PlaybackFollower 规则

- TrackFetched 是当前曲目的权威信号；当前曲目的开始时间 = 请求时间（实时转码来源另加约 4 s 缓冲偏移）。
- 兜底计时器：按“当前曲时长 + 余量”等待下一次 TrackFetched。超时后查询一次状态：`status=0` 判定为已停止；否则标记“跟随丢失”，在下一次用户操作时重发列表。
- 用户操作发出后，以它产生的第一个 TrackFetched 作为生效确认，取代现在的“开播确认轮询”。

### 状态权威（对 ADR-0004 的补充）

| 状态 | 权威 | 说明 |
|---|---|---|
| 歌单成员 | `music_library` | 不变 |
| 设备会话队列（顺序、版本号） | `SpeakerQueue` | 取代 `device_player._play_list_items` |
| 当前曲目与开始时间 | `PlaybackFollower` | 由 TrackFetched 驱动，取代计时器推测与 `cur_music` 多处写入 |
| 与小米云的通信 | `SpeakerClient` | 取代 `device_player` 中分散的 `mina_call`；mina/miio 两个空壳 transport 删除或改为包装它 |

### 不提供暂停 / 恢复

项目从未规划暂停功能（2026-11-22 Akari 确认），而且实测音箱无法原地恢复、也无法跳转。因此：

- 删除 `/api/v1/control/pause`、`/api/v1/control/resume`（v1 白名单 25 → 23）、WebUI 中未被页面使用的 `pause()` / `resume()`、`PlaybackPhase.PAUSED` 及相关的 arbiter 意图、transport 方法和测试。
- 语音“暂停”维持现状，按停止处理（`keywords_stop`）。
- 用户在音箱上手动暂停时，`status` 仍为 1，服务端看不出来；兜底计时器到点后若没有新的 TrackFetched，按“跟随丢失”处理。

在第 6 步删除前，现有暂停/恢复代码保持原样，不修、不扩展。

### 不支持队列的硬件

`play_by_url` 路径（不使用 `player_play_music` 的型号）只能逐首下发。保留现在的逐首模式作为后备，按硬件能力选择；StreamGateway 和 Follower 两种模式共用。

## 实施步骤

每一步都要通过行为测试和全量测试，在测试服完整构建并实机验收后再推送。

1. **StreamGateway（只读模式）**：新增稳定签名地址和请求合并，先只记录 TrackFetched、不改变播放行为；现有下发改用新地址。验收：各来源都能播，日志里 TrackFetched 与切歌一一对应。
2. **SpeakerClient**：把 `mina_call` 收进一个类，`device_player` 改为调用它。行为不变。
3. **SpeakerQueue + 队列下发**：按播放模式生成列表和 `loop_type`，自动切歌交给音箱；保留计时器但只做兜底。验收：各播放模式实机连续播放，不再出现重放开头。
4. **PlaybackFollower**：当前曲目改由 TrackFetched 驱动；删除逐首计时切歌、开播确认轮询，以及外部链接路径的那一套独立状态。
5. **合并入口**：API（外部链接）和本地歌单都走“生成队列 → 下发 → 跟随”这一条路径；`site_media` 的中转移入 StreamGateway。
6. **拆分与清理**：`device_player.py` 拆成 DevicePlayer / SpeakerQueue / PlaybackFollower；把 sid / LifecycleToken / 手动切歌代际 / barrier 收敛为每个队列的版本号；删除暂停/恢复（见“不提供暂停 / 恢复”）；用行为测试替换绑定内部实现的单元测试。

## 待确认问题

1. `loop_type=3` 的实际顺序（只用两首测过）。
2. 同一分组多台音箱：每台独立队列，地址里的 `did` 用于区分；是否需要同步起播待定。
3. 网站来源在拉流时才解析（约 3.5 s），会增加这一首的起播延迟；可以在前一首开始后预解析下一首，再按需要加入。
4. 窗口大小 N 的取值：越大续接越少，但每次手动操作的下发越慢（181 项约 3.7 s，3 项约 0.7 s）。先取 20，按实测调整。
5. 静音哨兵的实现：已用 60 s 静态静音文件验证可行；是否改为 StreamGateway 按需生成更长的静音流（应对超过 60 s 的云端卡顿），在实现时决定。

## 后果

### 正面

- 自动切歌不再依赖小米云，云端卡顿和“从头播几秒”不再出现在自动切歌中。
- 当前曲目由真实拉流请求确定，不再靠计时器推测。
- 各播放源对音箱是同一种地址，来源差异收在 Source 和 StreamGateway 两层。
- 播放模式交给音箱原生实现，顺序/单曲播放的“末尾停止”不再需要服务端发命令。
- 两条播放入口和多套过时判断机制可以收敛为一条路径、一个队列版本号。

### 负面

- 音频流全部经过 xiaomusic 中转，服务端要承担流量（局域网内）和一个新的常驻组件。
- 手动操作仍然经过小米云，体验与现在相同（偶发卡顿依然存在）。
- 迁移期间逐首模式与队列模式并存，需要按硬件能力切换并分别测试。
