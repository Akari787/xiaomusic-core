发布日期：2026-07-23
适用分支：`main`

## 1. 发布基线

本版本基于 `v1.1.2`，集中修复远端小米音箱的播放完成判定、启动确认、随机歌单 session 与 WebUI next/previous 控制链。

对比基线：

```bash
git diff --stat v1.1.2..v1.1.3
```

## 2. 播放稳定性修复

### 2.1 状态查询恢复为纯读

`get_offset_duration()` 只计算并返回进度，不再创建任务、查询设备或触发切歌。自动完成判定统一收口到 next timer 到期路径。

### 2.2 有限设备状态宽限

next timer 到期后不再无条件切歌：

- 音箱仍报告 playing 或状态未知时，最多延期三次，每次三秒；
- 第四次到期后推进下一首，避免小米设备长期报告 playing 导致永不切歌；
- 音箱连续两次明确报告未播放时，可以提前推进下一首。

### 2.3 非破坏性启动确认

后台启动确认失败不再通过同步 stop 重播同一首歌，避免歌曲开头反复播放。连续两次明确确认失败时沿当前队列安全推进。

### 2.4 修复后台任务自取消

后台确认任务触发下一首时，session bump 不再取消当前执行任务自身，避免播放流程停在 stop 与 play 之间，形成 `is_playing=true`、`duration=0`、无 timer 的半启动状态。

`get_offset_duration()` 同时增加 `_start_time<=0` 防御，不再输出 epoch 级假进度。

## 3. 随机歌单与控制链

### 3.1 统一播放入口

指定歌单随机播放继续使用：

```http
POST /api/v1/play
```

示例：

```json
{
  "device_id": "<device_id>",
  "query": "<playlist_name>",
  "source_hint": "auto",
  "options": {"shuffle": true}
}
```

服务端从结构化歌单 membership 选择起始成员，并根据 entity record 自动路由 Jellyfin 或本地来源。

### 3.2 稳定的随机 session

新播放 session 建立时只洗牌一次。手动 next、previous 与自动完成均沿同一运行时队列快照移动，不重新解析歌单、不重新洗牌，也不修改 `device.play_type`。

### 3.3 WebUI 只发送控制意图

修复 WebUI 在 next/previous 前先调用 `/api/v1/play` 点名目标曲目的问题。按钮现在只发送：

- `POST /api/v1/control/next`
- `POST /api/v1/control/previous`

完整链路统一为：

```text
WebUI
  → Public API
  → PlaybackFacade
  → PlaybackCoordinator
  → TransportRouter
  → XiaoMusicDevice._play_next / _play_prev
```

Facade 保持薄 RPC，不建立第二条队列导航旁路。

## 4. 来源解析与安全

- 随机歌单成员使用完整 entity record 构造 source payload，避免 Jellyfin 成员退化为占位媒体。
- 空歌单与未知歌单返回结构化 `InvalidRequestError`。
- Public API 响应递归脱敏 URL 中的 `api_key`、token、authorization、cookie 与 password；内部设备投递仍使用完整 URL。

历史版本中已进入响应的 Jellyfin API key 仍应在 Jellyfin 管理面板中轮换。

## 5. 文档与架构约束

新增 `docs/architecture/playback-control-model.md`，明确：

- `music_library` 是歌单事实来源；
- `XiaoMusicDevice` 是当前设备队列快照与索引权威；
- WebUI 只发送控制意图；
- 新 session 洗牌一次；
- next/previous 不得隐式调用新播放入口；
- 自动完成与手动导航汇入同一设备控制入口。

同步更新 API v1 契约、状态权威 ADR、系统总览与手工验收文档。

## 7. 已知边界

- 小米控制接口受认证刷新、云端限流和设备响应影响，单次 next/previous 可能出现明显延迟。
- 快速连续点击 next 的旧请求失效机制仍需后续专项强化；本版本没有引入 Facade 长锁或第二条导航路径。
- 人工听感仍取决于实际音箱、网络和媒体源状态。
