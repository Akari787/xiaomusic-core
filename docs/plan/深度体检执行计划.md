> 版本：v1.0

> 状态：计划阶段，尚未开始

---

## 一、目标

这次工作的目标不是：

- 修几个 bug
- 优化几个函数
- 重构几个文件

而是：

### 建立"长期可控的演化能力"

最终希望达到：

- 系统结构可理解
- 状态流可追踪
- 生命周期可管理
- API 边界稳定
- AI/Codex 不容易跑偏
- 重构风险可控
- 项目半年后仍能快速恢复上下文

---

## 二、项目背景

xiaomusic-core 当前阶段判断：**长期演化系统（Long-lived System）**

特征：
- API v1
- Source abstraction
- Runtime lifecycle
- SSE/WebUI 状态同步
- Auth restore
- 多来源播放
- React WebUI
- 自托管部署

此阶段最大的风险已经不是功能实现，而是**系统失控**。

**核心原则：AI 只能在规则内工作**

目标：
```
从"写代码"
转向
"管理系统演化"
```

### 阶段2：系统深度体检（并行执行）

**前置：** 阶段1 完成  
**目标：** 理解系统实际结构，建立架构文档  
**约束：** 禁止大规模重构。只观察、记录、建模、标记问题。

**并行任务说明：**
- 任务 S2-1, S2-2, S2-3 可以并行执行（都依赖 S1）
- 任务 S2-4, S2-5, S2-6 可以并行执行（都依赖 S1）
- S2-1~S2-6 之间无依赖关系

| 任务 | 内容 | 输出文件 |
|------|------|----------|
| S2-1 | Runtime 依赖图 | docs/architecture/runtime-dependency.md |
| S2-2 | 状态流图 | docs/architecture/state-flow.md |
| S2-3 | 生命周期审计 | docs/architecture/lifecycle.md |
| S2-4 | Source Abstraction 审计 | docs/architecture/source-system.md |
| S2-5 | Runtime God Object 审计 | docs/architecture/runtime-boundary.md |
| S2-6 | API Contract 审计 | docs/architecture/api-contract.md |

#### S2-1: Runtime 依赖图

**分析维度：**
- 完整调用链：入口 → API → Service → Runtime → Player → Transport → Source
- 谁持有状态（哪些类有 self.xxx 属性）
- 谁拥有生命周期（__init__ / __del__ / cleanup）
- 谁能跨层调用
- 谁能反向依赖（危险信号）

**输出格式：**
- mermaid flowchart 展示完整调用链
- 每个节点标注：文件名 / 职责 / 持有状态 / 生命周期问题
- 标记危险信号：跨层依赖、双向依赖、循环依赖

#### S2-2: 状态流图

**分析维度：**
- 事件源 → Runtime State → Player State → SSE → WebUI Frontend
- 是否存在多个权威状态源
- 是否存在 UI 层猜测状态（poll / setTimeout 轮询）
- 是否存在 runtime/player 状态漂移

**输出格式：**
- mermaid sequence diagram 展示状态变化流程
- 每个状态标注：权威者（唯一写入点）/ 观察者（只读）
- 标记危险信号：状态双写、轮询状态、状态漂移

#### S2-3: 生命周期审计

**分析维度：**
- 重点对象：runtime、SSE stream、auth task、playback session、async task
- 创建者 / 持有者 / 销毁者 是否明确
- 是否存在 zombie task（创建了无人销毁）
- 是否存在 ghost session（断线后残留）

**输出格式：**
```markdown
| 对象 | 创建者 | 持有者 | 销毁者 | 当前是否正确 | 风险备注 |
|------|--------|--------|--------|--------------|----------|
```

#### S2-4: Source Abstraction 审计

**分析维度：**
- 搜索 `if source ==` 和 `hasattr(source,` 模式
- 检查 Source 是否开始承担不该承担的职责（控制播放器、管理 auth、修改 runtime）
- 列出所有 source-specific hack

**输出格式：**
- 代码段列表：文件 / 行号 / 代码片段 / 原因
- 判断：是否违反 abstraction 原则
- 标记：插件化障碍点

#### S2-5: Runtime God Object 审计

**分析维度：**
- 统计 runtime.py 的代码行数、方法数、import 数
- 检查 runtime 是否承担了：auth 管理、player 管理、queue 管理、reconnect 管理、event 管理、source 管理
- 列出 runtime 的所有"不该属于它"的职责

**输出格式：**
- runtime.py 职责清单：方法名 / 职责描述 / 是否应该属于 runtime
- 依赖图：runtime 依赖了哪些模块，这些模块是否反向依赖 runtime
- 标记：God Object 症状（承担职责 > 5 个不同领域）

#### S2-6: API Contract 审计

**分析维度：**
- 列出所有 API endpoint
- 检查是否存在 WebUI 绕过 API 直接访问 runtime 内部状态
- 检查错误返回是否结构化
- 检查是否存在历史 API 漂移

**输出格式：**
- API 清单：method / path / 返回格式 / 错误格式
- 标记危险信号：非结构化返回、WebUI 绕过 API、状态同步机制缺失

#### S2.5-1: 状态权威偏差表

**前置文档：**
- docs/architecture/runtime-dependency.md
- docs/architecture/state-flow.md
- docs/architecture/lifecycle.md
- docs/architecture/source-system.md
- docs/architecture/runtime-boundary.md
- docs/architecture/api-contract.md

**分析步骤：**
1. 列出所有状态（从 state-flow.md）
2. 确定每个状态的"应有权威"（基于架构原则）
3. 确定每个状态的"当前实际权威"（从 dependency/flow/lifecycle 文档推断）
4. 填写偏差表

**输出格式：**
```markdown
| 状态 | 应有权威 | 当前实际权威 | 偏差说明 | 严重程度 |
|------|----------|-----------------|----------|----------|
| player state | runtime | ? | | 高/中/低 |
```

**质量门禁判断标准：**

- 只有偏差表完成且通过 Review，才能进入阶段3

#### S3-1: Event Model 定义

**分析维度：**
- 读取 xiaomusic/events.py，了解当前事件定义
- 搜索所有 emit() / publish() / send() 调用
- 确定当前触发方式（同步/异步）
- 列出所有事件名称和数据结构

**标准事件列表：**
```
PLAY_REQUESTED
SOURCE_RESOLVED
PLAYER_CONNECTED
PLAYER_DISCONNECTED
STREAM_FAILED
AUTH_EXPIRED
AUTH_RESTORED
QUEUE_UPDATED
PLAYBACK_STARTED
PLAYBACK_STOPPED
```

**约定决策表：**
| 约定项 | 决策 |
|--------|------|
| 触发方式 | 同步 emit / 异步 emit（二选一，必须统一） |
| emit 失败处理 | 抛出 / 吞掉 / 记录日志（三选一） |
| event bus 位置 | 全局单例 / 注入依赖（二选一） |
| 事件 schema 变更 | 必须走 ADR，禁止静默修改 |

#### S4-1: ADR 目录初始化

**ADR 列表：**
- 0001-api-boundary.md
- 0002-runtime-ownership.md
- 0003-source-abstraction.md
- 0004-state-authority.md
- 0005-event-model.md

**每个 ADR 格式：**
```markdown
# ADR-000X: 标题

## 状态： Accepted

## 上下文
（这个决策要解决什么问题）

## 决策
（我们决定怎么做）

## 后果
（这个决策会带来什么影响）
  - 正面
  - 负面
  - 未解决的问题
```

**ADR 触发条件（强制执行）：**
凡涉及以下变更，必须先有对应 ADR，否则 block merge：
- 修改 API contract
- 修改 runtime ownership
- 修改 event schema
- 修改状态权威归属
- 新增跨层依赖

#### S4-2: 系统宪法（constraints.md）

**禁止：**
```markdown
- WebUI 直接访问 runtime 内部状态
- Source 持有 runtime 引用
- runtime 特判 source 类型（禁止 if source == "xxx"）
- API 返回非结构化错误
- 绕过 event system 直接修改状态
- 无标注的 silent except（禁止裸 except: pass）
- 未经 ADR 修改 API contract / event schema
```

**必须：**
```markdown
- 所有状态变化通过 event system 通知
- 所有 async task 可取消，且有明确 owner
- 所有状态有唯一权威，并在 state-authority.md 中登记
- 所有生命周期明确 ownership（创建/持有/销毁）
- 所有临时方案必须标注 TEMP-HACK
```

**TEMP-HACK 治理规范：**
```python
# TEMP-HACK:
# reason: 解释为什么这样写
# remove_after: v1.x / 某个功能完成后 / 某个 bug 修完后
# related_issue: #123
# owner: 谁负责跟进
try:
    ...
except SomeError:
    pass  # 不允许不写原因
```

## 八、最终目标

### 系统可解释

任何模块，以下问题都能快速回答：
- 为什么存在
- 为什么这样设计
- 谁负责它
- 谁能修改它

### 状态可追踪

任何播放问题，以下问题都能追踪：
- 发生了什么
- 在哪一步失败
- 哪个状态漂移了
- 哪个 task 没有被销毁

### AI 可控

Codex 在规则内开发，而不是自由发挥。每次 PR 都经过 AI Review Checklist 过滤。

### 重构可执行

未来以下演化方向都能继续推进而不失控：
- Runtime 拆分
- Source 插件化
- SDK 提取
- AI Agent integration
- 多设备协同
