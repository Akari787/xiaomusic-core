ADR-0008：每台设备一个播放版本号 ​

  • 状态：Accepted（2026-11-23 Akari 认可；按“实施步骤”分步落地）
  • 日期：2026-11-23
  • 关联：ADR-0007 第 6 步（“把 sid / LifecycleToken / 手动切歌代际 / barrier 收敛为每个队列的版本号”）

上下文 ​

播放流程里几乎每一步都要回答同一个问题：“我手上这件事是不是已经过时了？”（用户又按了别的、队列已经换了、播放已经停了）。现在用五套计数器分别回答：

计数器什么时候前进谁在检查
sid（_play_session_id）_playmusic 开始、API 点播、停止计时器、后台任务、拉流事件；也是网关地址里的队列号
q（queue_session_id）只有 API 点播严格检查、屏障检查
c（command_generation）每个受理的命令（播放、停止、上下首、API 点播、自动切歌、失败重试）严格检查、命令执行前
a（track_attempt_id）每次实际下发（_playmusic、API 点播执行器）严格检查、屏障检查、下发返回后
切歌代际（_manual_nav_generation）用户命令和手动上下首（不含自动切歌、重试）_playmusic 和下发的各个阶段

另有两种组合判断：严格检查 = q、c、a 全等；屏障检查 = sid、q、a，特意不看 c（否则停止后排队的命令会把正在执行的停止判成过期）。

代价：

  1. 难读、难改：同一段代码里常常要连查三次（sid、token、切歌代际），漏查一处就是一个竞态。源码里约 230 处、测试里约 500 处引用。
  2. 语义不一致留下的隐患：用户命令受理后，旧队列在命令真正开始执行前仍被当作“当前队列”跟随；arbiter 对普通命令又是“后到的替换排队中的”，理论上旧窗口的哨兵或本地切歌产生的 AUTO_NEXT 能顶掉用户排队中的命令。
    • 更正（2026-11-23，动手写复现测试时重新推演）：现状下这几乎不可能发生。命令一开始执行，_playmusic 就推进 sid，旧队列随即失效；即便 AUTO_NEXT 先挤进去，它执行前的严格 token 检查也会因为用户命令推进了 a 而把它丢弃；剩下的只有“已受理、执行协程尚未运行”的毫秒级窗口，且跟随任务开头还会再查一次。起草时说成“1～2 s 的竞态”是夸大了。
    • 但第 3 步删掉 (q, c, a) 严格检查后，这些碰巧生效的保护就没有了，所以下面第 2 节的两条规则仍然需要，作为合并计数器的前提。

决策 ​

1. 一个版本号 ​

每台设备只有一个整数 version，在命令开始执行时前进（arbiter 工作协程取出命令后，执行任何物理操作之前）：PLAY、NEXT、PREVIOUS、AUTO_NEXT、RETRY、STOP 都前进一次。

  • 所有异步延续（计时器、开播确认、跟随、失败重试的等待、下发返回后的收尾）在创建时记下 version，执行前比较，不等即丢弃。
  • 网关地址里的队列号就是下发时的 version；拉流事件的队列号不等于当前 version 即为旧队列。
  • 一次命令执行内的多次下发（API 点播的备用地址）共用同一个 version，不再需要 a。
  • 停止是唯一的屏障。停止执行器只检查自己开始时的 version 有没有被另一个停止改变；排队在停止之后的命令不会让它过期，因为它们要等停止执行完才开始执行、才前进 version。因此不再需要“特意不看 c”的屏障检查。

2. 受理与执行分开 ​

  • 受理（API 返回之前，同步）：只做校验、更新给 WebUI 看的“目标曲目”、把命令交给 arbiter。受理不前进 version。
  • 用户命令一受理，当前队列即标记为“已被取代”：跟随逻辑不再处理它的拉流事件（不跟随、不因哨兵续接、不因过期重发），只记日志。这一条直接消除上面的竞态。
  • arbiter 的优先级：用户命令（PLAY / NEXT / PREVIOUS / STOP）可以替换排队中的任何命令；自动命令（AUTO_NEXT / RETRY）不能替换排队中或正在执行的用户命令，遇到时直接丢弃并记日志。

3. 删除 ​

q（并入 version）、c、a、切歌代际、LifecycleToken（换成一个 int）、屏障检查、navigation_generation 参数。TaskGeneration 改为只用 version。

4. 行为变化（相对现状） ​

场景现在之后
手动下一首受理后、执行前，旧窗口哨兵被拉取AUTO_NEXT 可能顶掉用户的“下一首”旧队列已被取代，不产生 AUTO_NEXT；用户的“下一首”照常执行
自动切歌正在执行时用户按下一首用户的命令排队，自动切歌执行完后再执行不变（用户命令替换排队中的、不打断正在执行的；执行中的自动切歌在下一个检查点因 version 前进而停止）
停止后紧接着播放播放排在停止之后不变
API 点播的备用地址第二次下发会让第一次的收尾判为过期共用一个 version；收尾只在最后一次下发后进行，结果相同

其余行为不变。

实施步骤 ​

每一步都先补行为测试（fake 音箱 + 真网关，见 tests/behavior/），全量测试通过，测试服实机验证后再推送。

  1. ✅ 受理即取代 + arbiter 优先级（2026-11-23）：用户命令受理时把当前窗口标记为“已被取代”（_supersede_queue，挂在 _invalidate_manual_navigation 和手动上下首的受理上），跟随逻辑忽略它的拉流事件；AUTO_NEXT / RETRY 在有用户命令排队（含排在停止之后）时被拒绝（IntentReceipt.accepted=False），但用户命令执行中仍可提交（失败策略在 PLAY 执行过程中提交 RETRY）。单元测试覆盖规则与接线（撤掉实现时全部失败）。
  2. 切歌代际 → version：手动上下首改为记录执行时的 version，删除 _manual_nav_generation 和 navigation_generation 参数。
  3. sid、q 合并为 version，删除 a、c、LifecycleToken、屏障检查。这一步会删掉大量绑定 (q, c, a) 的单元测试，事先用行为测试覆盖它们保护的场景（停止期间的各种命令、执行中的取消、过期的后台任务）。
  4. mixin 改为对象组合（ADR-0007 第 6 步剩余部分）：DevicePlayer 持有 SpeakerQueue、PlaybackFollower 等对象，各自只通过 version 判断过期。

修订（2026-11-23，实施第 2 步时） ​

动手后发现第 1 节“版本号在命令开始执行时前进”与现有、且被测试锁定的行为冲突，第 3 步“sid 并入 version”也不成立。修订如下（实现以本节为准）：

  1. 受理即前进：连按三次“下一首”时，第一次正卡在慢速停止里，后两次在此期间受理；现状是第一次在下一个检查点放弃，只下发最后的目标（test_rapid_next_presses_dispatch_only_the_final_target，单首与队列两条路径都有）。只在执行开始时前进的版本号做不到这一点。所以“当前命令”仍由受理时前进的命令代际 c 判断。第 2 步已据此把手动切歌代际换成 c（✅ 2026-11-23）。
  2. sid 不是 c 的重复：c 回答“哪个命令是当前的”（受理时前进）；sid 回答“音箱上是哪一批内容”（开始下发、停止、API 点播时前进），是网关地址里的队列号。失败重试、兜底计时器、拉流跟随都是“记下 sid → 提交自动命令 → 稍后确认仍是这批内容”；若 sid 换成 c，它们会在提交自己的命令后把自己判为过期（失败重试会失效）。逐处核对的 30 个使用位置都属于“内容”语义。
  3. 新终点：两个计数器——命令代际 c（受理）与队列号 sid（下发）。删除 q（只在 API 点播时前进，且总与 sid 同时前进）和 a（一次命令内的多次下发只发生在 API 点播的备用地址，且是同一协程里顺序进行），LifecycleToken 收缩为 (c, sid)，屏障检查改为只看 sid。
  4. “已被取代”标记（第 1 步）保留：它补上的是“c 已前进、sid 尚未前进”的那段时间。

剩余工作（删除 q、a，收缩 LifecycleToken）会改写约 220 处绑定 (q, c, a) 的旧单元测试，先等 Akari 确认修订后的方向再做。

后果 ​

  • 正面：过期判断只有一种写法；竞态的来源（受理和执行混在一起、旧队列仍被跟随）被消除；第 3 步预计再删一千多行代码和测试。
  • 负面：第 3 步改动面大，期间要依赖行为测试而不是旧的单元测试来保证正确；需要在测试服做较长时间的实机播放验证。

待确认 ​

  1. 第 2 节“自动命令不能替换用户命令”是否符合预期？（例如：用户刚点了一首歌、还没开播，此时旧队列的计时器到点——之后不会再切到旧歌单的下一首。）
  2. 是否同意按 1 → 4 的顺序分步做？第 1 步可以先单独做，不依赖其余部分。
